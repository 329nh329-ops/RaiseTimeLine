# 品質管理レビュー

このスキルは、単発のバグ探しではなく「実装がフレームワークの標準的なやり方に沿っているか」「品質を継続的に守る仕組み（lint）があるか」「ドキュメントが実装の実態を正しく反映しているか」という3つの異なる観点を、順番に・毎回セットで確認するためのものである。どれか1つだけをやって終わりにすると、次に呼ばれたときにまた同じ抜け漏れが起きるので、3ステップを一括りとして扱う。

## 全体の流れ

1. **ステップ1：実装レビュー** — コードを読み、指摘を洗い出し、どこまで直すかユーザーに確認する
2. **ステップ2：lint/静的解析** — 導入されていなければ入れる。入っていれば実行し、警告を解消する
3. **ステップ3：ドキュメント整合性チェック** — 全ドキュメントと実装を突き合わせ、ずれていたらドキュメント側を実装に合わせて直す

ステップ2・3で実際にファイルを変更する場合は、[CLAUDE.md](../../../CLAUDE.md)のGit/GitHub運用ルールに従う（Issue作成 → ブランチ作成 → 実装 → PR作成 → ユーザーのマージ承認を待つ）。ステップ1は指摘の洗い出しとユーザーへの確認までがこのステップの本体であり、実際の修正はユーザーの回答を踏まえてから着手する。

## ステップ1：実装レビュー（デファクトスタンダードからの逸脱チェック）

### 目的
「動いてはいるが、Spring BootやReactの標準的なやり方から外れている」実装を見つける。バグではなく、将来の保守性・拡張性・チーム開発での分かりやすさに関わる指摘が中心になる。

### やり方
1. バックエンド（`backend/src/main/java`配下）、フロントエンド（`frontend/src`配下）、インフラ（`infra`配下のTerraformコード）のソースコードを一通り読む。ファイル数が少ないプロジェクトなので、全部読むのが基本
2. 以下のドキュメントを読み、実装がその意図を正しく実現しているかも突き合わせる：[要件定義.md](../../../要件定義.md)、[docs/機能一覧.md](../../../docs/機能一覧.md)、[docs/機能定義/](../../../docs/機能定義/)配下の各ドキュメント、[docs/画面設計.md](../../../docs/画面設計.md)、[docs/データベース設計.md](../../../docs/データベース設計.md)、[docs/技術スタック.md](../../../docs/技術スタック.md)、[docs/インフラ構成.md](../../../docs/インフラ構成.md)
3. バックエンド（Spring Boot）で特に確認する観点：
   - **トランザクション境界**：1回の操作で複数レコードを更新・参照整合性を伴うServiceメソッドに`@Transactional`が付いているか（例：投稿削除時のコメント・いいねのカスケード、フォロー登録時の重複チェックと登録の一連処理）
   - **バリデーションの厳密さ**：本文の文字数上限、ユーザー名の文字数上限（`docs/データベース設計.md`のVARCHAR桁数と一致しているか）など、DB制約とアプリ側バリデーションが一致しているか
   - **認可チェックの徹底**：投稿・コメントの編集/削除、プロフィール編集が「本人のみ」に限定されているか（要件定義7章の非機能要件）。未ログイン状態でタイムライン等のAPIにアクセスできてしまわないか
   - **二重いいねの防止**：`LIKES_ON_POSTS`/`LIKES_ON_COMMENTS`のUNIQUE制約（post_id, user_id）（comment_id, user_id）に加え、アプリ側でも重合エラーを適切にハンドリングしているか
   - **パッケージ構成の一貫性**：`controller`/`service`/`repository`/`entity`/`dto`のような層別パッケージ構成を取っている場合、すべてのクラスがそのルールに従っているか
   - **例外処理の集約**：例外ハンドラが個別のControllerに直書きされておらず、`@RestControllerAdvice`のような共通の場所に集約されているか
   - **DBアクセスの効率**：いいね数・コメント数をアプリ側で全件取得してループ集計していないか（`docs/データベース設計.md`の方針通りCOUNTクエリで算出しているか）。N+1問題が起きていないか
4. フロントエンド（React）で特に確認する観点：
   - **データフェッチとuseEffectの扱い**：`useEffect`内で非同期データ取得を行っている箇所が、Reactの推奨パターン（依存配列の妥当性、クリーンアップの必要性）に沿っているか
   - **設定値のハードコード**：APIのベースURLなど、環境によって変わるべき値がソースコードに直書きされていないか（環境変数化すべきでないか）
   - **認証状態の管理**：未ログイン状態でのタイムライン等へのアクセス時にログイン画面へリダイレクトする仕組み（`docs/画面設計.md`10章）が実装されているか
   - **コンポーネントの責務・propsの数**：1つのコンポーネントが受け取るpropsが多すぎないか、関連するものはオブジェクトにまとめられないか
   - **命名の一貫性**：コールバック名などが実際の動作を正しく表しているか
5. インフラ（Terraform、`infra`配下、導入されていれば）で特に確認する観点：
   - **秘匿情報の直書き**：DBパスワード等の機密情報が`.tf`ファイルに直書きされていないか（`terraform.tfvars`等、Git管理対象外のファイルから変数経由で渡す形になっているか）
   - **`.gitignore`の網羅性**：tfstate（`*.tfstate`, `*.tfstate.*`）、`.terraform/`ディレクトリ、`terraform.tfvars`、`backend.hcl`、SSH秘密鍵（`*.pem`）、`.env.prod`など、コミットしてはいけないファイルが`.gitignore`に含まれているか
   - **ネットワークの開放範囲**：セキュリティグループのingressルールで、本来は自分のIPやVPC内に限定すべき通信（SSH、RDSへの直接アクセス）が`0.0.0.0/0`（全世界）に開かれていないか
   - **リソース間の一貫性**：`variables.tf`で定義した変数が実際に使われているか、複数ファイルにまたがるリソース参照（セキュリティグループID、サブネットIDなど）に誤りがないか
   - **フォーマット・構文チェック**：`terraform fmt -check`でフォーマットが揃っているか、`terraform validate`で構文エラーがないかを確認する（lintに相当するチェックとして、ステップ2でも実行する）
6. 見つけた指摘は、重要度がわかるように整理してユーザーに提示する（例：「認可漏れやトランザクション不足のような実際にバグ・セキュリティ問題につながりうるもの」と「命名や整理の話のような軽微なもの」を分けて説明する）

### 対応範囲の確認
指摘を提示したら、**必ず**ユーザーに「どこまで対応するか」を確認する（AskUserQuestion等で）。指摘して終わりにするか、重要度の高いものだけ直すか、全部直すかはユーザーの判断に委ねる。ユーザーが修正を選んだ場合は、CLAUDE.mdのルールに従いIssueを立ててから着手する。

## ステップ2：lint/静的解析の導入・実行

### 目的
一度見つけた問題を直すだけでなく、同種の問題を機械的に検出し続ける仕組みがあるかを確認し、なければ入れる。

### やり方
1. **フロントエンド**：`frontend/package.json`にlintスクリプトがあるか確認する（[docs/技術スタック.md](../../../docs/技術スタック.md)ではoxlintを`npm run lint`で実行する方針）。あれば実行し、警告が出ていれば修正する。無ければ導入する
2. **バックエンド**：`backend/build.gradle`にCheckstyleプラグインが入っているか確認する（[docs/技術スタック.md](../../../docs/技術スタック.md)の方針）。入っていれば`./gradlew checkstyleMain`（または`./gradlew check`）を実行し、警告・エラーがあれば内容を確認して対応する。入っていなければ、以下の方針で導入する：
   - `backend/build.gradle`に`checkstyle`プラグインを追加し、`./gradlew check`に組み込む
   - `backend/config/checkstyle/checkstyle.xml`に設定を書く。厳密なフォーマットルールよりも、未使用import、空のcatchブロック、文字列の`==`比較、`equals`/`hashCode`の不整合など、実際にバグにつながりやすい項目を中心にした軽量な設定にする（学習用の小規模リポジトリであり、過度に厳格なスタイル強制はノイズになる）
   - `MagicNumber`のような細かすぎるルールは、警告レベルを下げる（`severity: info`）か、バリデーションアノテーション内の値（`@Size(max = 30)`等）は`ignoreAnnotation: true`で対象外にするなど、実害のない指摘でビルドを止めないよう調整する
3. **インフラ（Terraform、導入されていれば）**：`infra`ディレクトリで`terraform fmt -check -recursive`（フォーマット崩れの検出）と`terraform validate`（構文・参照エラーの検出）を実行する。`fmt`で差分が出た場合は`terraform fmt -recursive`で整形し直す
4. 全て実際にコマンドを実行し、エラーなく通ることを確認してからステップ3に進む
5. lint/静的解析ツールを新規導入した場合、あるいは既存の設定を変更した場合は、[docs/技術スタック.md](../../../docs/技術スタック.md)にコード品質チェック体制として追記する（ステップ3の一部として扱ってもよい）

## ステップ3：ドキュメントと実装の整合性チェック・修正

### 目的
実装は正しく動いていても、ドキュメントが古いまま放置されていると、後から読む人（未来の自分を含む）が実態と異なる情報を信じてしまう。要件定義から派生した各ドキュメントを実装の実態に追従させる。

### やり方
1. 以下のドキュメントを全部読む：[要件定義.md](../../../要件定義.md)、[docs/機能一覧.md](../../../docs/機能一覧.md)、[docs/機能定義/](../../../docs/機能定義/)配下の各ドキュメント、[docs/画面設計.md](../../../docs/画面設計.md)、[docs/データベース設計.md](../../../docs/データベース設計.md)、[docs/技術スタック.md](../../../docs/技術スタック.md)、[docs/インフラ構成.md](../../../docs/インフラ構成.md)、[README.md](../../../README.md)（存在すれば`backend/README.md`、`frontend/README.md`も）
2. 各ドキュメントの記述を、対応する実装（ソースコード・DBスキーマ・実際のディレクトリ構成）と突き合わせる。特に見落としやすいパターン：
   - UIやAPIの仕様を途中で変更したとき、変更のきっかけとなったドキュメント（例：画面設計.md）だけ直して、それを参照している上位ドキュメント（例：要件定義.md）の該当箇所を直し忘れる
   - エンティティのフィールドの型を変更した（例：文字列からenumへ、IntegerからLongへ）のに、データベース設計書のテーブル定義が古い型のまま
   - 「詳細は実装時に決定する」（例：技術スタック.mdの認証方式のセッション/JWT）のような暫定的な記述を、実装が固まった後も具体化せずに放置している
   - リファクタリングでファイル配置やパッケージ構成を変えたのに、README等に載せているディレクトリ構成図が更新されていない
   - 機能が完成したのに、要件定義書の受け入れ基準（8章）のチェックボックスが未チェックのまま、あるいは古いスナップショットのまま
3. 見つかった不整合は、**実装を正としてドキュメント側を修正する**（このスキルは実装のリファクタリングではなくドキュメント整備が目的のため。ステップ1で見つかった実装側の問題は、ステップ1の指摘としてすでに扱っているはず）
4. 章番号や相互リンクを変更する場合は、他のドキュメントからその章番号を参照していないか（`grep`等で）確認し、リンク切れや参照ズレを起こさないようにする
5. 修正が完了したら、CLAUDE.mdのルールに従いIssueを立て、ブランチを切ってコミットし、PRを作成する

---

## 完了後

3ステップが終わったら、それぞれで何を見つけて、何を直したか（あるいは指摘のみに留めたか）を簡潔にまとめてユーザーに報告する。PRを作成した場合はそのURLも伝え、マージはユーザーの指示を待つ。
